  <name>Task 1: Service layer — CRUD orchestration with validation and audit trail</name>
  <files>src/modules/logbook/service.ts</files>
  <action>
Create `src/modules/logbook/service.ts` following `individual-tax/service.ts` layering (validate → business rules → repository → audit log). Named exports:

- `createLogbookForClient(input: { clientId: string; assessmentYear: number; vehicle: Omit<VehicleDetails, "id">; openingOdometer: number; closingOdometer?: number | null })` — `logbookCreateSchema.parse`; verify client exists via `getClientById(input.clientId)` (throw `Error("Client not found.")` when null — same guard as individual-tax); call `logbookRepository.createLogbook` (repository enforces the duplicate rule); `writeAuditLog({ action: "LOGBOOK_CREATED", entityType: "Logbook", entityId: created.id, summary: \`Created ${created.assessmentYear} travel logbook for ${created.vehicle.make} ${created.vehicle.model} (${created.vehicle.registrationNumber}).\` })`; return the record.
- `getLogbookForClientYear(clientId, assessmentYear)` and `listLogbooksForClient(clientId)` — thin repository pass-throughs (no audit on reads).
- `addTripToLogbook(logbookId, trip)` — `tripInputSchema.parse`; load the logbook (throw when missing); run `validateOdometerContinuity` over `{ openingOdometer, closingOdometer, trips: [...existing trips, newTrip] }` and THROW on any `errors` (message = joined error messages; warnings do not block — they surface later via the travel result); persist via `logbookRepository.addTrip`; audit `LOGBOOK_TRIP_ADDED`. This is the Pitfall-2 gate: continuity is enforced at the service boundary NOW so Phase 4's import reuses the same function instead of re-implementing it.
- `updateLogbookTrip(logbookId, tripId, patch)` — validate patch fields (a partial of `tripInputSchema` via `.partial()`); re-run continuity on the resulting trip set (existing trips with the patch applied); audit `LOGBOOK_TRIP_UPDATED`.
- `deleteLogbookTrip(logbookId, tripId)` — audit `LOGBOOK_TRIP_DELETED`.
- `updateLogbookOdometers(logbookId, odometers)` — `updateOdometersSchema.parse`; continuity re-check against existing trips (throw on errors); audit `LOGBOOK_ODOMETERS_UPDATED`. (LOG-02.)
- `setLogbookCostMethod(logbookId, costMethod)` — when electing `"ACTUAL"`, require the stored record to have complete `actualExpenses` (throw `Error("Capture actual expenses before electing the actual-cost method.")` when null); audit `LOGBOOK_COST_METHOD_SET`. The election is the ONLY thing that ever changes which method is claimed (Pitfall 1).
- `setLogbookActualExpenses(logbookId, expenses)` — `actualExpensesSchema.parse` (or accept `null` to clear — but refuse clearing while `costMethod === "ACTUAL"`); audit `LOGBOOK_ACTUAL_EXPENSES_SET`.
- `getLogbookTravelResult(logbookId): Promise<LogbookTravelResult>` — load record; resolve `const table = getIndividualTaxRulePackByYear(record.assessmentYear).travelDeemedCostTable` (Pitfall 4: NEVER `new Date().getFullYear()`, never trip dates); compute `totalKm = record.closingOdometer !== null ? record.closingOdometer - record.openingOdometer : null`, `businessKm = sum(trips.businessKm)` (unrounded sum); call `buildTravelResult({ businessKm, totalKm, costMethod: record.costMethod, vehicleCostPrice: record.vehicle.costPrice, actualExpenses: record.actualExpenses }, table)`; append any `validateOdometerContinuity` warnings to the result's warnings array; return it. This function IS the LOG-05 surface: one call returns the side-by-side comparison.

<task type="auto">
  <name>Task 2: Export functions — CSV serializer + audit summary (LOG-06)</name>
  <files>src/modules/logbook/export.ts</files>
  <action>
Create `src/modules/logbook/export.ts` with two PURE functions (no I/O, no repository import — they take a `LogbookRecord` and `LogbookTravelResult` so they are trivially callable from a Phase 6 route or an Electron save dialog):

- `exportLogbookToCsv(record: LogbookRecord): string` — RFC4180-style serializer, hand-rolled (serializing known internal data is fine; parsing arbitrary input is Phase 4's job and gets a library):
  - Header row: `Date,From,To,Reason,Business KM,Odometer Start,Odometer End`.
  - One row per trip, sorted by date ascending; empty string for null/undefined odometer values; numbers via `String(value)` (no locale formatting).
  - Escaping helper: wrap a field in double quotes when it contains a comma, double quote, `\r`, or `\n`; double any embedded quotes (`"` → `""`).
  - Join rows with `\r\n` (RFC4180 line ending). Return the string — the caller decides where it goes.
- `buildLogbookAuditSummary(record: LogbookRecord, travelResult: LogbookTravelResult): LogbookAuditSummary` — assemble the printable-summary data shape from types.ts: client id, assessment year, full vehicle details, opening/closing odometer, `totalKilometres`, `totalBusinessKm` (sum of trip businessKm, `r2`-rounded here at the output boundary), `tripCount`, trips sorted by date, the full `travelResult` (both methods side-by-side — this is what makes the summary SARS-audit-suitable), `generatedAt: new Date().toISOString()`.

Also add a convenience service-side wrapper in `service.ts` ONLY if it costs one line each (e.g., `getLogbookCsv(logbookId)` / `getLogbookAuditSummary(logbookId)` composing load + travel result + pure function); otherwise leave composition to callers. The printable PAGE (HTML/PDF route) is explicitly Phase 6 — this phase ships the data + CSV per the research's Open Question 3 resolution.
