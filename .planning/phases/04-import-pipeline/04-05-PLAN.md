  <behavior>
**detectSarsElogbookLayout(headers: string[]): DetectedMapping | null**

Normalization for matching: lowercase, trim, collapse internal whitespace, strip a leading `*`. Matching is ALWAYS by normalized header text, never by column index (Pitfall 3 — SARS revises the template; users reorder columns).

Alias table (SARS_ELOGBOOK_SIGNATURE), primary alias first:
- date: ["date"]
- businessKm: ["total business km", "business km", "business kilometres"]
- fromLocation: ["from"]
- toLocation: ["to"]
- reason: ["reason"]
- odometerStart: ["opening km", "opening kilometres"]
- odometerEnd: ["closing km", "closing kilometres"]

Rules:
1. All five MANDATORY fields (date, businessKm, fromLocation, toLocation, reason) must match, else null.
2. Odometer columns optional — absence never blocks detection (official template marks them not compulsory).
3. If two or more source headers normalize to aliases of the SAME field -> null (ambiguity is never guessed away).
4. confidence: "high" when every matched field matched its PRIMARY alias; "medium" when any field matched a secondary alias.
5. mapping values are the ORIGINAL header strings from the input (e.g. "*Opening Km", not the normalized form) so downstream row lookup works against parsed row keys.
6. matchedHeaders lists the original headers that participated in the mapping.
7. Unrecognized extra headers (e.g. "Actual Fuel & Oil Costs", "Notes") are ignored — they never block or degrade detection.

Cases: input -> expected
- Canonical official headers exactly as published (incl. `*Opening Km`, `*Closing Km`, both Actual-cost columns) -> DetectedMapping, confidence "high", odometer columns mapped
- Same headers REORDERED and in mixed case with padding (" DATE ", "total business KM") -> still detects, "high"
- "Business Km" instead of "Total Business Km" -> detects, confidence "medium"
- Headers missing "Reason" -> null
- Headers missing both odometer columns -> detects (odometers absent from mapping / null)
- Two columns both normalizing to "from" -> null
- Completely unrelated headers (e.g. an assessment export) -> null
- Empty header list -> null

**applyColumnMapping(rows: Record<string, string>[], mapping: ColumnMapping): RawTripCandidate[]**

- One candidate per input row, sourceRowIndex = array index; NEVER drops rows (invalid cells become null fields; validate-import decides row fate).
- date: `normalizeDateCell(row[mapping.date])` (handles DD/MM/YYYY, ISO, Excel-serial numeric strings)
- businessKm / odometerStart / odometerEnd: `parseNumericCell(raw)` where parseNumericCell handles: plain "123.5"; thousands spaces "1 234.5"; SA decimal comma "123,5" (single comma, no dot -> decimal separator); "1,234.5" (comma + dot -> thousands separator); empty/garbage -> null; negative numbers pass through (validation rejects them later with a clear error rather than the mapper hiding them)
- fromLocation/toLocation/reason: trimmed strings ("" when the column is unmapped or cell empty)
- odometer fields: null when mapping.odometerStart/End is null/undefined or the cell is empty/unparseable

Cases: input -> expected
- SARS-shaped rows with "15/03/2026", businessKm "120,5", odometers "10 000"/"10 120" -> candidate { date: "2026-03-15", businessKm: 120.5, odometerStart: 10000, odometerEnd: 10120 }
- Row with unparseable date "banana" -> candidate with date: null (row retained)
- Row with empty businessKm -> businessKm: null
- Mapping without odometer columns -> all candidates have null odometers
- Excel-serial numeric string date "45658" -> "2025-01-01"
- 3 in, 3 out — including one fully-garbage row (still emitted, all-null convertibles)
  </behavior>

  </implementation>
